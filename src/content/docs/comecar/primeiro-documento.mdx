Este é um tutorial autoral: monta um documento clínico do zero, explica cada
decisão de estrutura e valida o resultado. **Não exige credencial da RNDS**,
tudo aqui roda na sua máquina.

O objetivo não é produzir um documento pronto para produção e sim entender a
mecânica. Para os campos exatos do seu caso, a fonte é sempre o
[perfil publicado](/integracao/perfis-e-br-core/).

## Antes de começar

<Steps>

1. **Baixe um exemplo oficial.** Cada guia por modelo do Guia de Implementação
   tem uma página de exemplos com Bundles completos em JSON, como os
   [exemplos do REL](https://fhir.saude.gov.br/rel/pt-BR/exemplos.html). Um
   documento válido de verdade ensina mais rápido que qualquer descrição.

2. **Instale o validador.** É um JAR, roda offline:
   [releases do org.hl7.fhir.core](https://github.com/hapifhir/org.hl7.fhir.core/releases).

</Steps>

## Passo 1 - gere os identificadores primeiro

Esta é a inversão que pega todo mundo. Num documento FHIR, os recursos se
referenciam por `fullUrl`, e o `Composition` precisa apontar para recursos que
ainda não existem quando você começa a escrever.

A saída é gerar os UUIDs **antes** de montar qualquer coisa:

```js
import { randomUUID } from 'node:crypto';

const ref = () => `urn:uuid:${randomUUID()}`;

const id = {
  composition: ref(),
  resultado: ref(),
};
```

Agora você pode montar os recursos em qualquer ordem, porque toda referência já
tem destino conhecido. Repare que não há UUID para o paciente nem para o
laboratório: eles não entram no documento como recursos.

## Passo 2 - paciente e laboratório entram por identificador

Esta é a parte que mais contraria a intuição de quem já conhece FHIR. O paciente
**não entra no documento** como um recurso `Patient`: o perfil exige a
referência pelo identificador, com um `system` fixo, e proíbe apontar para um
recurso. O laboratório segue o mesmo padrão, pelo CNES.

```js
const SD = 'http://www.saude.gov.br/fhir/r4/StructureDefinition';

const paciente = {
  identifier: { system: `${SD}/BRIndividuo-1.0`, value: '<CPF ou CNS do paciente>' },
};

const laboratorio = {
  identifier: { system: `${SD}/BREstabelecimentoSaude-1.0`, value: '<CNES do laboratório>' },
};
```

O `system` é a URL de um perfil, não de um NamingSystem. Parece errado, mas é o
que os perfis da RNDS fixam. Veja em [identificadores](/integracao/identificadores/).

<Aside type="danger" title="Nunca use dado real">
Dado de saúde é dado pessoal sensível sob a LGPD, com regime mais restritivo que
o de dado pessoal comum. Não use dado real de paciente em desenvolvimento e não
coloque documento clínico real em repositório, nem privado.
</Aside>

## Passo 3 - o Composition vem primeiro, sempre

Para Bundles do tipo `document`, a especificação FHIR é normativa: **a primeira
entrada é obrigatoriamente um `Composition`**. Ele é o índice do documento - não
contém os dados clínicos, aponta para quem contém.

```js
const composition = {
  resourceType: 'Composition',
  meta: { profile: [`${SD}/BRResultadoExameLaboratorial-3.2.1`] },
  status: 'final',
  type: {
    coding: [{
      system: 'http://www.saude.gov.br/fhir/r4/CodeSystem/BRTipoDocumento',
      code: 'REL',
    }],
  },
  subject: paciente,
  date: new Date().toISOString(),
  author: [laboratorio],
  title: 'Resultado de Exame Laboratorial',
  section: [{
    entry: [{ reference: id.resultado }],
  }],
};
```

O `meta.profile` declara o perfil que o recurso segue. É por ele que o validador
sabe contra o que conferir, e todos os recursos dos exemplos oficiais o trazem.

## Passo 4 - o resultado do exame

```js
const resultado = {
  resourceType: 'Observation',
  meta: { profile: [`${SD}/BRDiagnosticoLaboratorioClinico-3.2.1`] },
  status: 'final',
  subject: paciente,
  performer: [laboratorio],
  issued: new Date().toISOString(),
  // category, code, effective, value, method, specimen e referenceRange
  // também são obrigatórios neste perfil.
};
```

<Aside type="caution">
O documento deste tutorial está incompleto de propósito. No resultado, o perfil
do REL exige ainda categoria, nome do exame, data da coleta, valor, método,
amostra e faixa de referência, cada um com códigos de terminologias específicas.
E a seção do `Composition` precisa apontar também para um `Condition`, a
condição de saúde do paciente. O caminho mais curto é copiar a estrutura do
[exemplo oficial](https://fhir.saude.gov.br/rel/pt-BR/exemplos.html) e trocar os
valores.
</Aside>

## Passo 5 - empacote o Bundle

```js
const bundle = {
  resourceType: 'Bundle',
  identifier: {
    system: 'http://www.saude.gov.br/fhir/r4/NamingSystem/BRRNDS-<número do solicitante>',
    value: '<identificador único do documento no seu sistema>',
  },
  type: 'document',
  timestamp: new Date().toISOString(),
  entry: [
    { fullUrl: id.composition, resource: composition },
    { fullUrl: id.resultado,   resource: resultado },
  ],
};
```

Repare que cada entrada casa `fullUrl` com o UUID gerado no passo 1, e que a
referência do `Composition` para o resultado aponta para esse mesmo valor,
**nunca para um ID de banco de dados**.

O `Bundle.identifier` é o identificador local do documento. Guarde-o junto com o
ID que a RNDS devolve no envio: sem os dois não há como consultar, substituir
nem excluir o documento depois. Veja em [serviços](/integracao/servicos/).

## Passo 6 - valide

```bash
java -jar validator_cli.jar documento.json \
  -version 4.0.1 \
  -ig https://fhir.saude.gov.br/rel/package.tgz
```

Valide contra o pacote do modelo, publicado em
`https://fhir.saude.gov.br/{modelo}/package.tgz`, e não contra o BR Core: os
perfis da RNDS não derivam dele. Veja em
[perfis e BR Core](/integracao/perfis-e-br-core/).

Rode primeiro contra o exemplo oficial, para confirmar que o ambiente está
certo, e depois contra o seu documento. Na conferência deste guia, em 30/10/2026
com o validador 7.0.3, o exemplo oficial do REL passou sem erros com esse
comando.

Neste tutorial o validador vai acusar o que falta no resultado e na seção, e
isso é esperado: cada erro traz a URL do perfil violado, e a lista vira o seu
roteiro. Se você trocar o identificador do paciente por um `Patient` dentro do
documento, ele acusa também `Composition.subject.reference: max allowed = 0`.

## Passo 7 - leia de volta

Ler é a metade que costuma ser subestimada. Navegar índice a índice
(`bundle.entry[3].resource...`) funciona no primeiro documento e quebra no
segundo, porque a ordem das entradas não é garantida.

<Tabs>
<TabItem label="Índice de fullUrl">

```js
const porUrl = new Map(
  bundle.entry.map((e) => [e.fullUrl, e.resource])
);

const comp = bundle.entry[0].resource;
const paciente = comp.subject.identifier.value; // não está no documento
const resultados = comp.section[0].entry.map((r) => porUrl.get(r.reference));
```

</TabItem>
<TabItem label="FHIRPath">

```
Bundle.entry.resource.ofType(Composition).subject.identifier.value
```

Devolve o CPF ou CNS do paciente, ou vazio em vez de explodir se o campo não
existir. Veja em [FHIRPath](/ferramentas/fhirpath/).

</TabItem>
</Tabs>

## O que fazer em seguida

- Baixe **todos** os exemplos oficiais e use como fixtures dos seus testes
- Coloque a validação no CI, para pegar regressão antes do barramento
- Escreva casos de teste **negativos**, código fora do ValueSet, dígito
  verificador inválido, campo obrigatório ausente. O barramento rejeita por
  motivos que não aparecem nos exemplos.
- Leia os [erros comuns](/erros-comuns/) antes de gastar tempo com eles
